# المعمارية — Kawalis China Sourcing MVP v1.0

## A) المعمارية العامة

```
┌─────────────────────────────────────────────────────────┐
│                    العميل (المتصفح)                       │
│   الهبوط  /  فورم الطلب (6 خطوات)  /  صفحة التتبع        │
└──────────────────────────┬──────────────────────────────┘
                           │ HTTPS — JSON فقط (DTOs)
┌──────────────────────────▼──────────────────────────────┐
│              Next.js API Routes (server-side)            │
│  /api/requests   إنشاء طلب + رقم فريد + تسجيل تواصل      │
│  /api/track      تحقق هوية → DTO مسموح فقط               │
│  /api/quotes/feedback   رد العميل على العروض المعتمدة    │
│  /api/upload     رفع صور → Vercel Blob                   │
│  ┌───────────────────────────────────────────────────┐  │
│  │ zod validation → rate limit → dedupe → lib/notion │  │
│  └───────────────────────────────────────────────────┘  │
└──────────────────────────┬──────────────────────────────┘
                           │ Notion API (المفتاح server فقط)
┌──────────────────────────▼──────────────────────────────┐
│            Notion — نظام التشغيل الداخلي (SSOT)          │
│  Sourcing Requests ←→ Suppliers ←→ Quotations            │
│           └──────── Communications                       │
│  الفريق يعمل هنا بالكامل: مراجعة، بحث، عروض، تفاوض       │
└─────────────────────────────────────────────────────────┘
```

قرارات مقصودة لتجنب الـ overengineering:
- **لا قاعدة بيانات خارجية ولا ORM** — Notion هو المخزن الوحيد في الـ MVP.
- **لا نظام مصادقة** — التحقق للعميل = رقم الطلب + جوال/بريد مطابق.
- **لا لوحة إدارة ويب** — Notion نفسه هو لوحة الفريق (Views + Kanban).
- **لا قاعدة خامسة للـ Activity Log** — التعليقات الداخلية عبر `Internal Notes`
  وتعليقات صفحات Notion المدمجة (تعطي تاريخاً كاملاً بأسماء وأوقات مجاناً)،
  بينما التفاعلات المهمة مع العميل تُسجل بنيوياً في قاعدة Communications.
  قاعدة خامسة تضيف صيانة بلا قيمة تشغيلية في هذه المرحلة.

## B) خريطة قواعد Notion

انظر NOTION_SETUP.md للخصائص الكاملة. الملخص:

- **Sourcing Requests** (المركز): بيانات العميل والمنتج والحالة (24 حالة).
- **Suppliers**: المورد يُسجل مرة واحدة ويُربط بطلبات متعددة.
- **Quotations**: كل عرض = طلب واحد + مورد واحد. عرض السعر كيان مستقل
  بتاريخه الكامل (أولي → تفاوض → نهائي → مقبول/مرفوض).
- **Communications**: كل تفاعل مهم مع العميل (يدوي من الفريق + تلقائي من الموقع).

## C) رحلة العميل

1. يفتح الصفحة → "ابدأ طلب توريد" أو "لدي طلب قائم".
2. يعبّئ 6 خطوات: تواصل → منتج → كمية/ميزانية → تخصيص → شحن → إضافي.
3. عند الإرسال: تحقق → رقم فريد → حفظ في Notion → شاشة نجاح برقم الطلب.
4. يتتبع طلبه في أي وقت (رقم الطلب + جوال/بريد): حالة، خط زمني،
   تحديث الفريق، الخطوة القادمة.
5. عندما يعتمد الفريق عروضاً: يراها العميل ويرد عليها
   (مهتم / تعديل / تفاوض / **اختيار**) — وردّه يُسجل تلقائياً في Notion.
6. بعد الاختيار: يتابع مراحل العينة والتصنيع والفحص والشحن حتى التسليم.

## D) رحلة الفريق (داخل Notion بالكامل)

```
طلب جديد يصل تلقائياً (01) + سجل Communications
→ مراجعة الطلب (02) وتعيين مسؤول وأولوية
→ التواصل مع العميل وتسجيله في Communications (03 إن نقصت معلومات)
→ البحث عن موردين (04) وربطهم بالطلب (05)
→ طلب عروض أسعار (06) وإدخالها في Quotations (07)
→ مراجعة العروض داخلياً (08) وكتابة Customer Visible Notes
→ تفعيل Approved For Customer + تحديث Customer Visible Update (09)
→ انتظار قرار العميل (10) — ردوده تصل تلقائياً من الموقع
→ تفاوض (11) بتحديث نفس صفحة العرض (التاريخ محفوظ)
→ العميل يختار → الحالة تتحول تلقائياً (12)
→ الفريق يسجل Selected Supplier/Quotation ويتابع (13→21)
→ مكتمل (22) أو متوقف (23) أو ملغي (24)
```

### الـ Views المقترحة في Notion

**Requests**: Kanban حسب Status • جدول شامل • تقويم على Next Follow-up Date •
"متابعات اليوم" (فلتر: Next Follow-up Date = Today) • فيوهات مفلترة:
جديدة / تحتاج مراجعة / بانتظار العميل / جاري البحث / عروض / بانتظار قرار /
قيد التنفيذ / الشحن / مكتملة / متوقفة / ملغية.

**Suppliers**: الكل • موثقون • قيد التحقق • مصانع • شركات تجارية • حسب الفئة.

**Quotations**: الكل • جديدة • قيد المراجعة • قيد التفاوض • نهائية • مقبولة • مرفوضة.

**Dashboard**: صفحة Notion تجمع Linked Views مفلترة: طلبات جديدة، متابعات اليوم،
جاري البحث، لديها عروض، بانتظار قرار العميل، قيد التنفيذ، تم شحنها، مكتملة.

## E) النموذج الأمني

1. **المفاتيح**: `NOTION_API_KEY` ومعرفات القواعد في متغيرات بيئة server فقط.
2. **الوصول للبيانات**: العميل لا يصل لـ Notion إطلاقاً — فقط عبر API routes
   التي تعيد DTOs بحقول مصرح بها صراحة (whitelist في `lib/dto.ts`).
3. **التتبع**: رقم الطلب وحده لا يكفي — يجب تطابق الجوال (آخر 9 أرقام،
   يشمل الواتساب) أو البريد. رسالة فشل واحدة لا تكشف سبب الرفض.
4. **العروض**: بوابة `Approved For Customer` — قرار صريح من الفريق لكل عرض.
   رد العميل يُقبل فقط على عرض معتمد وتابع لطلبه المتحقق منه.
5. **رقم الطلب**: `KC-RFQ-<سنة>-<5 أرقام عشوائية>` مع فحص عدم الوجود في Notion
   قبل الإنشاء وإعادة المحاولة — لا عدّ للصفوف، لا تصادم عند التزامن.
6. **الحماية**: rate limiting لكل IP (5 طلبات/10 دقائق على المسارات الحساسة)،
   submission token يمنع الإرسال المزدوج، Zod يرفض أي مدخل خارج المخطط،
   الرفع مقصور على صور ≤ 5MB.
7. **الأخطاء**: للعميل رسائل عربية ودية؛ التفاصيل التقنية في سجلات الخادم فقط.

## F) مراحل التنفيذ

| المرحلة | المحتوى | الحالة |
|---|---|---|
| 1 | هبوط + فورم + رفع صور + رقم فريد + إنشاء في Notion + نجاح | ✅ منفذة |
| 2 | قواعد Notion الأربع + العلاقات (يدوياً عبر NOTION_SETUP.md + سكربت فحص) | ✅ موثقة ومفحوصة |
| 3 | صفحة التتبع + الحالة + الخط الزمني | ✅ منفذة |
| 4 | العروض المعتمدة + رد العميل + الاختيار | ✅ منفذة |
| 5 | إشعارات بريد/واتساب آلية | 🔜 مرحلة قادمة (تتطلب مزود خارجي) |

## G) تعديلات أوصي بها (منفذة)

1. **`Approved For Customer` checkbox** في Quotations بدل الاستدلال من حالة
   التفاوض — تحكم صريح بما يراه العميل.
2. **رقم عشوائي بدل تسلسلي** في Request ID — الـ Notion API لا يوفر عدّاداً
   ذرياً، والتسلسل الحقيقي يتطلب مخزناً خارجياً (تعقيد بلا حاجة في MVP).
3. **بدون قاعدة Activity Log خامسة** — Internal Notes + تعليقات Notion
   + Communications تغطي الحاجة (انظر A).
4. **الإشعارات مؤجلة للمرحلة القادمة** — كل مزود (Resend / WhatsApp API)
   يتطلب حسابات واعتمادات خارجية؛ فصلناها حتى لا تعطل إطلاق الأساس.
